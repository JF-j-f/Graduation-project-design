1.只有当收到 “撰写工作总结” 命令时，才执行以下指令：
README 是项目的脸面。仅当项目的**“What (是什么)”、“How (怎么用)”** 或 “Why (核心技术)” 发生本质变化时，才更新此文档。

4.1. 项目核心结构 (Core Structure)
策略：对 Project 根目录下所有子目录进行全量文件扫描，当前目录结构要与文件系统的1:1还原！
触发条件：只要文件系统发生了任何文件的新增或删除（无论文件大小或类型），均判定为项目结构变更，必须触发 README 更新。
内容要求：使用纯文本注释，仅解释该文件/目录的职责，不记录具体的代码改动细节。
注释规范 (红线)：
  客观描述：仅描述文件/目录的功能（如 # 封面下载工具）。
  符号禁令：严禁使用 []、()、【】 等标记符号（如 [NEW], (核心)）。
  零时间属性：注释中不得包含“今天”、“最新”、“旧版”等时间相关词汇。

4.2. 技术架构与工具栈 (Tech Stack)
策略：保持高层视角。
触发条件：
核心框架变更：例如从 Servlet 升级到 Spring Boot，或从 MySQL 换成 PostgreSQL。
关键版本跃迁：例如 Java 8 -> 23，Node 14 -> 20。
新增基础设施：例如引入了 Redis、Docker 或全新的 Python 微服务模块。
不更新内容：某个小工具库的小版本升级（如 gson 2.8.6 -> 2.8.9）不需要写在这里。

4.3. 部署与启动流程 (Deploy & Run)
策略：这是对开发者最重要的部分，追求**“一步到位”的准确性**。
触发条件：任何会导致“按照文档操作却跑不起来”的变更。
例如：新增了必须的环境变量、启动命令变更（如从 npm start 变为 pm2 start）、新的数据库初始化脚本。
不更新内容：内部逻辑优化、性能提升等不影响部署操作的内容。

4.4. 核心功能特性 (Features)
策略：面向最终用户/产品经理的介绍。
触发条件：
新增业务板块：例如上线了“歌单系统”、“评论区”等用户可见的大功能。
功能废弃：某个旧功能被彻底移除。
不更新内容：Bug 修复、UI 微调、后台逻辑优化。

4.5. 数据库设计
策略：链接数据库，获取当前与项目有关的核心业务表的结构，更新对应表的字段。
触发条件：每次执行更新都需要进行！
例如：songs表的字段发生了变化，比如增加了一个xxx字段，则在文档的songs表中也要新增该字段。

4.6. 你还需要更新该文档最后的更新时间，位于文档的最底部。

📝 4.7. 更新日志规范
核心原则：日志必须同时具备“可回溯性”（过去做了什么）与“前瞻性”（未来要做什么）。拒绝流水账，每一条记录都应对应代码的实体变更。

板块详规 (必填)：

🚀 新增功能
定义：记录新加入的、用户或开发者可见的功能特性。
写作要求：
UI/交互类：简述新的交互逻辑（如“新增右键菜单...”）。
接口/逻辑类：需注明关键类名或端点（如“新增 ImageProxyServlet支持图片直读”）。
❌ 错误示范：新增了功能。
✅ 正确示范：新增 ImageProxyServlet模块，拦截 /img/* 请求以直接读取源码目录资源。
🐛 Bug 修复
定义：记录已修复的具体缺陷。
写作要求：采用 “现象 + 成因 (可选) + 结果” 的格式。让阅读者能对应到自己遇到的问题。
✅ 正确示范：修复了 Tomcat 重启后导致本地上传封面丢失 (404) 的问题，修正了路径映射逻辑。
⚡性能优化
定义：代码重构、性能提升、资源精简或体验改进（非功能性变更）。
写作要求：指出具体的优化点（如“减少了内存占用”、“废弃了冗余逻辑”）。
✅ 正确示范：优化封面下载策略，废弃了“运行目录+源码目录”的双重保存机制，降低 IO 开销。
🚧 待解决问题
定义：记录开发过程中已发现但暂未修复、或故意留到下一阶段解决的问题。
重要性：这是项目交接和断点续传的关键。必须具体，严禁使用“有一些小 Bug”这种模糊描述。
✅ 正确示范：Last.fm API 尚未接入，导致欧美小语种歌曲的“流派”字段依然为空。
📝 拟解决方案
定义：针对 Known Issues 的技术思考或行动指南。
写作要求：
可以是具体的代码思路（“使用 Flex 布局重写...”）。
也可以是待调研的方向（“计划调研 redis-pipeline 优化批量查询...”）。
✅ 正确示范：计划申请 Last.fm API Key，并编写 GenreProvider 接口对接其 track.getInfo 端点。
